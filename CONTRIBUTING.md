# Як працювати з репозиторієм

## Головне правило

У `main` напряму ніхто не пушить. Будь-яка зміна потрапляє в `main` тільки через Pull Request.

`main` — це те, що працює на сервері. Після злиття в `main` сайт оновлюється сам.

## Гілки

| Префікс | Для чого | Приклад |
| --- | --- | --- |
| `feature/` | нова функція | `feature/cart` |
| `fix/` | виправлення помилки | `fix/login-redirect` |
| `infra/` | сервер, Docker, CI/CD | `infra/nginx-https` |

Назви латиницею, маленькими літерами, через дефіс. Одна гілка — одна задача.

## Порядок роботи

1. Оновити `main`:
   ```
   git checkout main
   git pull
   ```
2. Створити гілку:
   ```
   git checkout -b feature/cart
   ```
3. Робити коміти. Повідомлення коротко по суті: що змінено.
4. Запушити гілку:
   ```
   git push -u origin feature/cart
   ```
5. На GitHub відкрити Pull Request у `main`, коротко написати що і навіщо.
6. Дочекатися ревʼю і виправити зауваження.
7. Злиття тільки через **Squash and merge**: один Pull Request = один коміт у `main`.
8. Гілка після злиття видаляється автоматично.

## Ревʼю

- Схвалює інший учасник, не автор.
- Якщо після схвалення додали нові коміти, схвалення скидається і треба переглянути ще раз.
- Усі обговорення в Pull Request мають бути закриті до злиття.
- Коли з'явиться CI, злити можна тільки після зелених перевірок.

## Секрети

- Жодних паролів, токенів і ключів у коді. Репозиторій публічний, їх побачать усі.
- Локально секрети лежать у файлі `.env`. Він у `.gitignore` і в репозиторій не потрапляє.
- Зразок змінних без значень — у `.env.example`.
- На сервері і в CI — тільки GitHub Secrets.
- GitHub сам блокує пуш, якщо знайде схоже на пароль. Не обходьте блокування: приберіть секрет із коду і напишіть адмінам, ключ треба буде замінити.

## Середовище

- Усе запускаємо через Docker, щоб у всіх було однакове середовище.
- Двофакторна автентифікація (2FA) обов'язкова для всіх в організації.
